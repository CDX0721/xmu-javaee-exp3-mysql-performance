# 基于 MySQL 的 Spring 应用读写性能测试与瓶颈定位

陈泓冰（22920242203172）

**摘 要**：数据库访问是以 MySQL 为后端的 Spring 应用的主要瓶颈，而性能上限究竟由容器与应用框架的参数（最大线程数、连接池、数据库连接数）决定，还是由硬件算力决定，往往缺乏定量证据。本实验在四台 2 vCPU 华为云虚机组成的 Docker Swarm 集群上，用课程提供的 JMeter 循环模式脚本（ramp-up 10 s、每线程 1 次迭代）对同一个 Spring Boot + JPA 应用的读（按主键查商品）、写（创建商品）两个 RESTful 接口阶梯加压，以"80% 的请求响应时间小于 40 ms"为判据。读接口从 500 请求加压到 6500 全部达标（p50 恒为 2~3 ms），施加速率被爬坡量化推到约 1000 请求/s 的 6750 档起骤塌（达标率 47.1%→11.6%），此时唯一饱和的是应用所在虚机的 CPU（97%~99.5%），数据库虚机仅 14%~18%。参数消融将 Tomcat 最大线程数（32→1000）、Druid 连接池、MySQL max_connections（300→64）逐层收紧或放大，吞吐上限始终停在 760~1310 req/s；把三层上限同时放大到 1000/1000/1000，临界档照样全塌（应用机 CPU 仍 99.4%~99.5%、数据库机仍 14%~16%），写接口临界档反而因请求同时拥入而恶化到 p50=6.2 s；而把应用容器的 CPU 配额从 2 核压到 1 核，上限立即从约 1020 降到约 503 req/s（比值 1.9），两种配额下折算出的每请求 CPU 成本同为 1.9~2.0 ms。写接口最高通过 950 请求档（90.0% 达标、库机 CPU 82%），施加速率逼近 106 req/s 天花板的 975 档起不达标（库机 CPU 98%），此后吞吐钉死在 105.8~106.8 req/s，饱和点始终是 MySQL 虚机（CPU 100%、1 分钟负载峰值 146），磁盘 I/O 全程 ≤2.6%、内存 ≤61%。本实验的结论是：读写两条路径的容量上限都由"可用 CPU 时间 ÷ 每请求 CPU 成本"决定，与线程数、连接数无关，这些参数真正决定的是队列出现在哪一层。最后据此给出降低每请求 CPU 成本、建立二级索引与水平扩展三条优化建议。

**关键词**：MySQL；Spring Boot；JPA；JMeter；Prometheus；性能测试；瓶颈定位；参数消融

**Read and write performance of a MySQL-backed Spring application: what really sets the ceiling**

Chen HongBing（22920242203172）

**Abstract**: Database access is commonly the dominant bottleneck of Spring applications backed by MySQL, yet whether the capacity ceiling is set by container and framework parameters (maximum threads, connection pools, database connections) or by raw compute is rarely supported by quantitative evidence. On a four-VM Docker Swarm cluster of 2-vCPU Huawei Cloud instances, we step-load two RESTful APIs of one Spring Boot + JPA application — a primary-key product read and a product creation — with the course-provided JMeter 5.6.3 loop-mode script (10 s ramp-up, one iteration per thread), using "80% of requests under 40 ms" as the acceptance criterion. The read path passes every level from 500 to 6000 requests (p50 steady at 2 ms) and collapses at 8000 (36.8% passing), where the only saturated machine is the application VM (CPU 97%–99.5%; the database VM stays at 18%). Ablating Tomcat max threads (32→1000), the Druid pool, and MySQL max_connections (300→64) leaves the throughput ceiling unchanged at 760–1310 req/s, while cutting the application container's CPU quota from 2 cores to 1 immediately halves it to about 503 req/s (ratio 1.9); the implied per-request CPU cost is 1.9–2.0 ms under both quotas. The write path passes at 500 requests (97.2%) and fails at 1000, after which throughput is pinned at 105.8–106.8 req/s and saturation moves to the MySQL VM (CPU 100%, 1-minute load up to 146) while disk I/O stays under 2.6% and memory under 61%. We conclude that the ceiling of both paths is "available CPU time divided by per-request CPU cost", independent of thread and connection limits, which merely decide where the queue forms. Three optimisation directions — reducing per-request CPU cost, adding secondary indexes, and scaling out — are given.

**Key words**: MySQL; Spring Boot; JPA; JMeter; Prometheus; performance testing; bottleneck analysis; parameter ablation

## 1 问题描述

在基于数据库的应用中，数据库访问是系统的主要瓶颈之一。对同一个 Spring Boot + JPA 应用，读接口（按主键查商品）与写接口（创建商品）的容量上限可以差一个数量级以上，而"上限由什么决定"却常有两种互相竞争的解释：一种归因于部署参数——Tomcat 最大线程数、Druid 连接池、MySQL 连接数等；另一种归因于虚机的算力本身。本实验不预设哪一种正确，而是在同一套环境上回答四个问题：

1. 在"80% 的请求响应时间小于 40 ms"判据下，读、写两个接口在循环模式加压下各自能通过多大的档位？吞吐上限是多少？
2. 档位塌掉的那一刻，饱和的是哪一台虚机、哪一层？如何排除发压端欠拟合与监控假象？
3. 逐层收紧或放宽线程/连接参数，上限跟不跟着变？如果不跟，真正决定上限的量是什么、能否用对照实验钉死？
4. 写接口的卡点与读接口是否在同一处？差异能否定量解释？

实验在四台华为云 ECS 组成的 Docker Swarm 集群上进行：发压端、应用端、数据库端与监控端分处四台独立虚机，四者的资源占用可以分开测量——这是把瓶颈归因到具体一台机器的基本条件。

### 2.2 实验方法

测试用课程提供的 `jmeter-command.sh` 以非 GUI 模式运行：`sh jmeter-command.sh ReadProduct 8000 10 1` 表示以 8000 线程、10 s 爬坡、每线程 1 次迭代执行 `ReadProduct.jmx`，原始记录写入 `ReadProduct-8000-10-1.jtl`，并用 `jmeter -e -o` 生成 HTML 报告。判据与取数方式如下：

- **判据的读法**。"80% 的请求响应时间小于 40 ms"等价于 P80 ≤ 40 ms，直接读报告 Charts → Response Times → **Response Time Percentiles** 曲线上横坐标 40 ms 对应的百分比；由于报告不直接输出该数值，同时用脚本对 `.jtl` 的 `elapsed` 列逐行统计 `<40 ms` 比例作为表内数值，两者互相核对。平均响应时间不作为判据：均值把长尾摊平，且随并发平滑上升，而达标比例在临界档陡降，用均值会高估容量近一倍。
- **吞吐与分位数**取自该档报告的 `statistics.json`（注意其中 `pct1ResTime` 是 p90、`pct2ResTime` 是 p95，按名字读会错一档）；样本数与错误率取自 `.jtl`。
- **服务端侧的旁证**来自 Prometheus。按指导书要求配置的三个 Query 是 `spring:jvm_threads_live_threads`（各服务活跃线程数）、`node:cpu_usage_percent`（各节点 CPU 利用率）、`node:memory_usage_percent`（各节点内存使用率），其曲线形态见图 1~图 3。
- **但录制规则不能用来定位饱和**。`node:*` 录制规则的窗口是 `rate(...[5m])`、步进 30 s，而本实验一档只有 8~10 s：同一时段 B 机 CPU 用录制规则看峰值只有 31.5%（图 2），回到原始指标 `rate(node_cpu_seconds_total{mode="idle"}[15s])` 才能看到反复顶到 97% 以上（图 4）。`scrape_interval=2s` 下 `[15s]` 窗口有 7 个采样点，够稳且不漏峰；再短开始抖，再长就开始摊平——`[1m]`/`[30s]`/`[15s]`/`[5s]` 四种窗口下 B 机 8000 档 CPU 峰值分别为 46.9%/63.8%/97.3%/99.5%。同理，"磁盘读写字节速率"（图 9、图 10）是吞吐量不是利用率，论证"没卡在磁盘"必须用 `node_disk_io_time_seconds_total` 折算的 I/O 利用率（图 8）。本文所有表格中的四机 CPU、内存、磁盘、负载数值，均为按档位实际起止时间用 `/api/v1/query_range`（`rate[5s]`）回查的档内峰值，与本报告截图的 Prometheus 查询界面同源。
- **查询界面的时间口径**：本版本 Prometheus 的 End time 按 UTC 解析，读接口全部档位落在 UTC 2026-10-22 23:36~23:53（北京时间 23 日 07:36~07:53），写接口落在 UTC 23 日 03:14~03:21（北京时间 11:14~11:21）；下文 Prometheus 截图横轴均为 UTC。
- **服务端并发与 JVM 线程**用 `http_server_requests_active_seconds_count`（Long Task Timer，同时在处理中的请求数）与 `jvm_threads_live_threads` 读取；容器内 `process_cpu_usage` 恒为 0，CPU 只能用 node-exporter 的原始指标。

### 2.3 实验设计

**阶梯设计**。两个接口各自从低档到高档逐级加压：读接口 M = 60（冷启动首档）、500、1000、1500、2000、3000、4000、6000、8000；写接口先跑一档 `warmW`（M=60）预热，再跑 M = 500、1000、1500、2000、3000、4000、6000。主阶梯定出临界区间后，再对区间二分细化（读：6500、6750、7000；写：750、900、950、975），每个新档位都在同一预热状态、同一配置下与相邻档对照，并复测一个已知档位作同环境锚点（读 6000/8000、写 1000）。ramp-up 固定 10 s、loop=1，每档只变 M。每档结束后用 `crit.py` 直接判 PASS/FAIL，四机资源曲线按档窗口回查，避免"看着图讲故事"。

**M 的语义必须先说清楚**。loop=1 时 M 是"请求总数"而不是并发数：响应为毫秒量的档位里，线程发完即走，结果文件中的 `allThreads` 峰值远小于 M（6000 档只有 26，8000 档因服务端变慢才积压到 576）。因此本实验不把 M 叫"并发"，各档结论只回答"以 M/10 请求每秒的速率施压能否达标"；真正的临界并发从 8000 档的 Time Vs Threads 图反读——响应时间越过 40 ms 的临界并发正好落在 40~50（图 14），与固定时长模式独立测得的 40 并发互相印证。

**爬坡的整数毫秒量化**。JMeter 计算线程启动间隔时取整数毫秒，8000 档为 `(long)(10×1000/8000)=1 ms`，10 s 的爬坡实际被截成约 8 s（实测样本跨度 7.8 s），瞬时施加速率从标称 800 请求/s 翻倍到 1000 请求/s。也就是说 8000 档的实际负载恰好压在服务端的墙根上，这不是巧合，而是读这条结论时必须交代的量化效应。

**每档复跑**。临界档单独复跑以排除偶然性：默认配置的 8000 档独立运行 6 次（跨两个会话，见 2.4 节表 8），吞吐落在 805~1020 req/s（均值约 930，±12%），而达标率恒在 11%~37% 之间、判据稳定不达标——"这一档不通过"的结论是稳的，"上限的具体数值"则如实报成区间。

**写测试的库状态控制**。写请求会向 `goods_product` 插入新行，而写路径的开销与表规模相关。为使各档之间只有"施加速率"这一个变量，每档写测试结束后删除本实验插入的行（`delete from goods_product where id > 5573`，只按主键边界删除，不 truncate、不动其他表），使下一档从同一基线 3 913 行开始。固定时长下 20 s 即可写入约 2 000 行，若不逐档清理，"速率变高"与"表变大"两个效应会混在一起，拐点无法归因。

**冷启动控制**。每次重新部署后 JVM 的 JIT 是冷的，首个档位的 p95 会虚高约 75 倍（实测 608 ms，预热后 8 ms）。因此每次部署后先跑 3 轮 `2000 10 1` 预热再开始记录；写接口的 `warmW` 档就是本轮的预热档。

**原始数据归档**。`jmeter-command.sh` 的产物名只由 `<jmx>-<M>-<T>-<loop>` 决定，同名档会被直接覆盖，因此跑完即把 `.jtl` 与报告目录归档到带备注的目录（详见附录 A），老师提供的脚本本身一个字没有改。

两点必须如实说明，否则这张表会被读错：

- **4000、6000 档的 λ 低于标称（337<400、505<600）是发压端欠拟合，不是服务端限制**。这两档 A 机（发压机）CPU 已到 86%/96%，线程起不满（图 15），而 B 机 CPU 只有 49%/45%，仍有余量。

**临界档二分**。主阶梯只给出"6000 通过、8000 不通过"，边界用二分细化：复测会话中 6000 与 6500 档通过（p80 仅 7/3 ms），6750 与 7000 档不通过，**读接口最高通过档为 6500**。边界两侧的差别不在请求数本身，而在实际施加速率：6500 档发压端只递出约 500 请求/s（样本跨度 12.8 s，A 机 CPU 91%、线程起不满），6750 档的爬坡却被压缩到 6.6 s、施加速率跳到约 1020 请求/s，一步越过应用机 2 vCPU 的承受能力——服务端并发随即顶满 `threads.max=300`（inflight_max=300）、B 机 CPU 99.5%。所以"最高通过的线程数"物理上是最高可持续施加速率的参数化形式：6000/6500 档 B 机 CPU 只有 57%~90% 是发压端欠拟合，6750/7000 档立即顶满才是真实的墙。

#### 2.4.3 参数消融：三层上限逐个掐小，拐点不动

老师上课推测上限可能出在部署参数（数据库连接数、最大线程数）上。验证方法是消融：其余层不动，一次只收紧（或放大）一层，看临界档跟不跟着变。改参数只需改部署文件 `command:` 块的 4 行并 `docker stack deploy` 重建任务（MySQL 的 `max_connections` 例外，在 C 机 `my.cnf`，改完必须 `docker service update --force lab_mysql` 并确认容器 `StartedAt` 已变化）；每次重新部署后先跑 3 轮预热档消掉冷 JIT。结果见表 5。

**表 5 参数消融**（每配置跑 `4000 10 1`、`8000 10 1`、`2000 10 8` 三档，"λ / p50"单位为 req/s 与 ms；"—"表示该档未跑）

| 配置 | 4000 档 λ / p50 | 8000 档 λ / p50 | 2000×8 档 λ / p50 | 同时处理峰值 | 服务端自报RT(ms) | B机CPU(%) |

消融的四条读法：

- **吞吐上限与这三层参数无关**。五种配置的 λ 全部落在 760~1310 req/s，参数从 32 扫到 1000 都没能把它推开；同时每一种饱和档里 B 机 CPU 都是 90%~99.5%。上限不在参数里。
- **参数改变的是队列落在哪一层**，`threads.max=32` 一行最明显：Tomcat 只同时处理 32 个请求，队列排在容器外面，服务端自报的平均 RT 只有 27~30 ms，代价是客户端 TCP 建连时间从 0.7 ms 涨到 47.2 ms；默认 300 时队列搬进服务端，自报 RT 涨到 211 ms，但客户端 p50 反而是所有配置里最好的。
- **把线程开到 1000 是负优化**：JVM 线程冲到 563，B 机 CPU 99.3%，λ 掉到全场最低的 790、p50 涨到 1349 ms——2 个核上堆上千个可运行线程，多出来的全是上下文切换与缓存失效。
- **正面否证"数据库连接数"猜想**：把 MySQL 上限从 300 掐到 64（远小于 300 个 Tomcat 线程），吞吐只从 871 降到 720 且错误率仍为 0。B 机日志里抓到 91 次 `errorCode 1040 Too many connections`，但全部集中在同一秒——那是 Druid 建连线程整批被拒的瞬间，之后连接池退回与并发相称的规模，请求只是排队（p95 从 633 涨到 1565 ms）而不失败。原因很容易算：主键读每请求只占用连接约 2 ms，64 条连接按 Little 定律足以支撑每秒数万请求。该档 C 机 CPU 全程只有 11.5~18.5%，`Innodb_row_lock_waits` 增量为 0。

**三层同时放大也没有用**——这是"上限由部署参数决定"猜想里唯一没测过的组合，单独补测。把 Tomcat `threads.max`、Druid `max-active`、MySQL `max_connections` 三层同时从 300 放大到 1000，重新部署并预热后复测临界档，结果见表 6：三个临界档依旧全塌，B 机 CPU 仍 99.4%~99.5%、数据库机仍 14%~16%，天花板纹丝不动；写 975 档反而显著恶化——Tomcat 放行 596 个请求同时拥入（`inflight_max` 从 18 涨到 596）、743 个 JVM 线程在 2 核上互相踩踏，p50 从默认配置的 34 ms 恶化到 6.2 s。**放大参数不会抬高上限，只会把排队从容器外搬进系统内部、塌得更难看。**

#### 2.4.4 决定性对照：把应用容器的 CPU 配额砍半

消融只能证明"改参数没用"，不能证明"有用的那个是什么"。反向证据只需一条命令、不改任何文件：`docker service update --limit-cpu 1 lab_productdemoaop`，把应用容器的 CPU 配额从 2 核压到 1 核。结果见表 7。

**表 7 CPU 配额对照**（λ 单位 req/s，p50 单位 ms）

| 应用可用核数 | 6000 档 λ / p50 / 同时处理 | 8000 档 λ / p50 | B机整机CPU(8000档) |
|---|---|---|---|
| 2（默认，无限额） | 505 / 2 / 2 | 934~1020 / 134~594 | 97.1% |
| **1（--limit-cpu 1）** | 460 / **1085** / **300** | **503~534** / 4227 | **67.9%** |

- **砍一半 CPU，吞吐上限几乎正好砍一半**：1020 → 503，比值 1.9~2.0；6000 档同时处理的请求数从 2 涨到 300（线程池重新被填满）。
- **每请求 CPU 成本在两种配额下算出来是同一个数**：1 核 ÷ 503 req/s = 2.0 ms；2 核 × 97% ÷ 1020 req/s = 1.9 ms。说明被消耗的是同一个与并发无关的量——上限 = 可用 CPU 时间 ÷ 每请求 CPU 成本。

写为什么这么贵，可以在同一基线上单独测得：1 并发下每个写请求在数据库侧扫描约 3.46 万行——`ProductService.createProduct()` 在 `save()` 之后组装返回对象，附带对 `goods_goods`（30 282 行）与 `goods_onsale`（3 850 行）的两个无索引查询，只能整表扫描。C 机 2 核打满、吞吐 106 req/s 对应每请求约 19 ms 数据库 CPU 时间，与万行级的扫描量一致；读接口每请求只扫描 1 行，每请求 CPU 成本仅 1.9~2.0 ms 且大头在应用侧 JVM。读写两个数量级的差距由此定量落地。

## 3 总 结

本实验在四台 2 vCPU 虚机的 Swarm 集群上，用课程提供的循环模式脚本对读、写两个接口做了阶梯加压、监控定位、参数消融与配额对照，得到的核心结果是：

1. **读接口**：500~6500 请求档全部通过（p50 恒 2~3 ms；最高通过档 **6500**，98.6% 达标），施加速率被爬坡量化推到约 1000 req/s 的 6750 档起不通过（达标率 47.1%→11.6%，两个会话 6 次运行一致）；塌掉时唯一饱和的是应用所在虚机 B 的 CPU（97%~99.5%），数据库机仅 14%~18%，发压机 95%~96%。临界并发从 Time Vs Threads 反读为 40~50。
2. **写接口**：500~950 档通过（最高通过档 **950**：90.0% 达标、p80=24 ms、库机 CPU 82%），975 档起不通过（施加速率约 100 req/s，贴上 106 req/s 天花板，库机 CPU 98%），1500 档起吞吐钉死在 105.8~106.8 req/s；饱和点在数据库虚机 C（CPU 100%、负载峰值 146），应用机 CPU 反而降到 19%~37%。全程零错误，磁盘 I/O ≤2.6%、内存 ≤61%、行锁等待为 0。
3. **上限与线程/连接参数无关**：Tomcat `threads.max` 从 32 扫到 1000、Druid 池同步放大、MySQL `max_connections` 掐到 64，读的吞吐上限始终停在 760~1310 req/s；三层同时放大到 1000/1000/1000 也一样，读临界档依旧全塌（B 机 CPU 仍 99.4%~99.5%）、写 975 档反而恶化到 p50=6.2 s；而应用容器 CPU 配额从 2 核压到 1 核，上限立即掉半（1020→503，比值 1.9），两种配额折算的每请求 CPU 成本同为 1.9~2.0 ms。

三个结果合起来的结论是：**读卡应用机的 CPU，写卡数据库机的 CPU；两条路径的容量上限都等于"可用 CPU 时间 ÷ 每请求 CPU 成本"，既不是线程数、也不是连接数**。线程/连接参数真正决定的是队列出现在哪一层（`threads.max=32` 时队列在容器外、服务端自报 RT 仅 27 ms 但建连涨到 47 ms；300 时队列搬进服务端）——把它们调大解决不了上限，调得比核数还多反而是负优化（1000 线程档 λ 最低、p50 最高；三层同放到 1000 时写临界档 p50 恶化约 180 倍，见表 6）。

据此给出三条优化建议，按投入产出排序：

1. **降低每请求的 CPU 成本**。主键读每请求只扫 1 行，1.9~2.0 ms 几乎全花在 JVM 内（Spring MVC 分发、JPA 实体映射、VO 拷贝、AOP 切面）：给热点商品加应用级缓存、让接口只取必要字段，是抬高读上限的直接手段。
2. **为作为查询条件的列建立二级索引**（`goods_goods(product_id)`、`goods_onsale(product_id)` 等）。写路径每请求约 3.46 万行的扫描全部来自组装返回对象时的两个无索引查询，索引可直接削减数据库机的 CPU 成本，即写接口的 106 req/s 上限。
3. **加算力或水平扩展**。应用被节点约束钉在 B 机，2 核是硬墙；要验证扩展需先把本地构建的镜像推到镜像仓库、放开节点约束。注意读上限的瓶颈在应用机、写在数据库机，两侧要分别扩。

方法层面本实验的可复用结论有三条：其一，循环模式下 M 是请求总数而非并发数，临界并发要从 Time Vs Threads 反读或改用固定时长模式校验；其二，判饱和必须回到 `rate[15s]` 级别的原始指标，分钟级录制规则（`rate[5m]`）会把 8~10 s 的饱和档摊平成"一切正常"的假象；其三，区分"参数到了顶"与"算力到了顶"只能靠消融加决定性对照，本实验的 `--limit-cpu 1` 一条命令即完成反证。
